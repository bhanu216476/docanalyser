# Document Metadata Architecture & Specification

## 1. Why Metadata is Required

In a production Retrieval-Augmented Generation (RAG) system, raw unstructured document text alone is insufficient for reliable operation. Metadata provides critical context, governance, and traceability across the document lifecycle:

- **Identity & Lifecycle Tracking**: Differentiating versions of documents, tracking document ingestion and processing stages (`PENDING`, `PROCESSED`, `FAILED`).
- **Deduplication & Content Addressing**: Detecting identical documents submitted under different filenames or at different times using cryptographic content hashing (`content_hash`), avoiding duplicate chunking and vector storage costs.
- **Source Attribution & Citations**: Enabling RAG answers to cite exact source paths and filenames back to the original documents.
- **Filtering & Access Control**: Supporting metadata-based pre-filtering and post-filtering during dense and hybrid retrieval (e.g., filtering by file type, creation date, or status).
- **Auditability & Observability**: Knowing document size, MIME type, creation/update timestamps, and pipeline failure reasons.

## 2. Ingestion Lifecycle & Service Boundaries

The pipeline adheres to clean separation of concerns:

```text
Source File (.txt, .md)
       │
       ▼
[Python RAG Service]
   1. Loader (TxtLoader, MarkdownLoader)
       │
       ▼
   2. Loaded Document (raw text, basic properties)
       │
       ▼
   3. Metadata Normalizer (deterministic canonicalization, SHA-256 hashing)
       │
       ▼
   4. Canonical DocumentMetadata
       │
       ▼ (Future API / Service Boundary)
[Spring Boot Service]
   5. Document JPA Entity (UUID primary key, timestamps)
       │
       ▼
   6. DocumentRepository (Spring Data JPA)
       │
       ▼
[PostgreSQL Database]
   7. `documents` table (Flyway migration V1)
```

### Responsibility Boundaries:
- **Python RAG Service (`rag-service`)**:
  - File reading, parsing, format cleaning, and canonical metadata normalization.
  - Generates deterministic SHA-256 content hashes, canonicalizes extensions, and infers MIME types.
  - Out of scope today: direct persistence to PostgreSQL.
- **Spring Boot Backend (`backend/spring-boot-service`)**:
  - Domain modeling, persistence boundary, entity lifecycle management, and relational database migrations via Flyway.
  - Spring Data JPA repository operations.
- **PostgreSQL**:
  - Durable, relational single-source-of-truth for document metadata, indexes, and primary key generation.

## 3. Document Identity Strategy

### Decision: Database-Generated UUID Primary Key

Documents are identified by a **UUID** (`gen_random_uuid()` in PostgreSQL / `GenerationType.UUID` in JPA), **not** by filename or path.

### Rationale:
1. **Filename Collision**: Files with the same name (e.g. `README.md`, `report.txt`, `annual_review.pdf`) frequently exist in different folders, branches, or customer uploads.
2. **Path Mutability**: Storage paths and source URLs change over time due to migrations, renaming, or storage restructuring.
3. **Immutability**: A synthetic UUID guarantees an immutable, non-colliding identifier across all services (Python, Java, database, and client applications).
4. **Deduplication Support**: Content equivalence is managed via `content_hash` (SHA-256), allowing multiple submissions of identical files to be correlated or deduplicated without colliding on primary keys.

## 4. Canonical Metadata Model

The cross-service contract between Python, Spring Boot, and PostgreSQL is defined as:

| Field | Python Type | Java Type | PostgreSQL Column | Description |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `Optional[UUID]` | `UUID` | `UUID PRIMARY KEY` | Immutable document ID (generated by DB/ORM) |
| `file_name` | `str` | `String` | `VARCHAR(255) NOT NULL` | Basename of originating file (e.g. `guide.md`) |
| `file_type` | `str` | `String` | `VARCHAR(50) NOT NULL` | Canonical extension without dot, lowercase (e.g. `txt`, `md`) |
| `mime_type` | `str` | `String` | `VARCHAR(100) NOT NULL` | Canonical IANA MIME type (e.g. `text/plain`, `text/markdown`) |
| `source` | `str` | `String` | `TEXT NOT NULL` | Normalized source path or URI |
| `file_size` | `int` | `Long` | `BIGINT NOT NULL` | Size in bytes (non-negative integer constraint) |
| `content_hash` | `str` | `String` | `VARCHAR(64) NOT NULL` | Deterministic SHA-256 hexadecimal hash |
| `status` | `DocumentStatus` | `DocumentStatus` | `VARCHAR(20) NOT NULL` | Ingestion status (`PENDING`, `PROCESSED`, `FAILED`) |
| `created_at` | `Optional[datetime]`| `Instant` | `TIMESTAMPTZ NOT NULL` | UTC creation timestamp |
| `updated_at` | `Optional[datetime]`| `Instant` | `TIMESTAMPTZ NOT NULL` | UTC last updated timestamp |

## 5. PostgreSQL Schema & Flyway Migration

The database schema is managed via Flyway migration:
`backend/spring-boot-service/src/main/resources/db/migration/V1__create_documents_table.sql`.

```sql
CREATE TABLE IF NOT EXISTS documents (
    id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
    file_name VARCHAR(255) NOT NULL,
    file_type VARCHAR(50) NOT NULL,
    mime_type VARCHAR(100) NOT NULL,
    source TEXT NOT NULL,
    file_size BIGINT NOT NULL CHECK (file_size >= 0),
    content_hash VARCHAR(64) NOT NULL,
    status VARCHAR(20) DEFAULT 'PENDING' NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL
);

-- Index on content_hash for deduplication and content-addressed lookups
CREATE INDEX IF NOT EXISTS idx_documents_content_hash ON documents (content_hash);

-- Index on status for pipeline processing state queries
CREATE INDEX IF NOT EXISTS idx_documents_status ON documents (status);
```

### Constraints & Indexes:
- `id`: UUID Primary Key with `gen_random_uuid()` default.
- `CHECK (file_size >= 0)`: Enforces non-negative file size at the database level.
- `idx_documents_content_hash`: Enables fast deduplication lookups when checking if identical content was previously ingested.
- `idx_documents_status`: Accelerates pipeline queries querying unprocessed (`PENDING`) or failed (`FAILED`) documents.

## 6. Python Metadata Normalization Rules

Implemented in `rag-service/app/ingestion/metadata_normalizer.py`:

1. **File Name**:
   - Stripped of surrounding whitespace; non-empty validation. Preserves user filename without mutation.
2. **File Type**:
   - Stripped of leading dots, lowercase.
   - Canonical mappings:
     - `.TXT`, `txt`, `TXT` &rarr; `txt`
     - `.md`, `.MD`, `.markdown`, `MARKDOWN` &rarr; `md`
     - `.pdf` &rarr; `pdf`
     - `.html`, `.htm` &rarr; `html`
3. **MIME Type**:
   - Deterministic mapping:
     - `txt` &rarr; `text/plain`
     - `md` &rarr; `text/markdown`
     - `pdf` &rarr; `application/pdf`
     - `html` &rarr; `text/html`
   - Fallback: `application/octet-stream` for unrecognized formats.
4. **Source**:
   - Normalized cross-platform using forward slashes (`/`), avoiding Windows backslash inconsistencies.
5. **File Size**:
   - Represented as non-negative integer in bytes (`ge=0`).
   - Inferred from content UTF-8 byte length if not provided by loader stat.
6. **Content Hash**:
   - Deterministic SHA-256 cryptographic hash calculated on raw UTF-8 content bytes.
   - Same content guaranteed to produce identical 64-character lowercase hex digest.
7. **Document Status**:
   - Enum with controlled states:
     - `PENDING`: Initial state upon metadata extraction.
     - `PROCESSED`: Document successfully chunked, vectorized, and persisted.
     - `FAILED`: Ingestion or parsing failure.

## 7. Security & Configuration Best Practices

- **Zero Credentials in Git**: All database connection parameters use environment variables (`DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USERNAME`, `DB_PASSWORD`, `POSTGRES_USER`, `POSTGRES_PASSWORD`).
- **Configuration Templates**: `.env.example` provides complete template variables without sensitive defaults.
- **Flyway-Driven Schema**: Schema management uses Flyway versioned migrations; Hibernate `ddl-auto` is set to `validate` in production/dev to prevent automated destructive changes.
- **Isolated Testing**: Spring Boot tests execute against an in-memory database in PostgreSQL compatibility mode with Flyway validation enabled, ensuring tests run reliably across CI/CD and developer workstations.
